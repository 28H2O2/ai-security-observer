# ASO Risk Score v1.0

ASO Risk Score 用于比较已有公开证据的安全漏洞和攻击机制。评估对象需要说清攻击入口、受影响系统和安全后果。纯观点、教程、风险分类框架，以及无法界定单一安全问题的方法研究，可以不评分。

这是本站自定义的 0–100 指标，非 CVSS、EPSS，也不是经过统计校准的攻击概率。初版不划分“高危”“严重”等区间。分数表示这套规则下的比较结果，不能代替对实际部署的判断。

## 规则与证据

规则版本为 `aso-risk-v1.0`。程序中唯一的规则来源是 [`dist/risk-rules.js`](../dist/risk-rules.js)，构建、页面和排序均引用它。公式由确定性程序计算：

```text
RiskScore = 7 × I + 5 × F + 4 × S + 4 × A
```

四维只能填写 0–5 的整数或 `null`。`null` 表示未知；四维缺一项，总分就是 `null`，不插值、不补零。权重合计 100%，来源可信度和人工复核状态不参与计算。

### I · 安全后果（Impact，35%）

| 分值 | 锚点 |
| --- | --- |
| 0 | 未体现实际安全边界损害 |
| 1 | 轻微输出偏离、有限功能干扰 |
| 2 | 有限的信息暴露或操作异常 |
| 3 | 明确的未授权操作、敏感数据暴露或权限滥用 |
| 4 | 严重数据泄露、关键系统操作失控或高影响攻击后果 |
| 5 | 严重代码执行、高权限系统接管、大规模敏感数据失陷等重大后果 |

### F · 可利用性（Feasibility，25%）

| 分值 | 锚点 |
| --- | --- |
| 0 | 只有理论假设，尚无合理攻击路径 |
| 1 | 依赖非常苛刻的环境、权限或复杂条件 |
| 2 | 需要多个非默认前置条件或较高攻击能力 |
| 3 | 可通过正常工作流接触的低信任内容触发，例如网页、文档或工具返回 |
| 4 | 攻击门槛低，通常不需要特殊权限，利用路径较直接 |
| 5 | 能够远程、无需认证、无需额外用户交互地直接触发 |

### S · 影响范围（Scope，20%）

| 分值 | 锚点 |
| --- | --- |
| 0 | 尚无明确的受影响对象 |
| 1 | 仅限实验环境、罕见配置或特定个人系统 |
| 2 | 影响特定产品、平台或配置 |
| 3 | 影响明确的生产产品及一部分常见部署 |
| 4 | 涉及多个广泛使用的产品或部署场景 |
| 5 | 涉及大规模部署的核心基础组件或广泛的 AI 系统生态 |

### A · 利用证据（Activity，20%）

| 分值 | 锚点 |
| --- | --- |
| 0 | 已确认目前没有公开 PoC 或在野利用证据；不代表攻击不存在 |
| 1 | 存在具体攻击路径或初步可行性分析 |
| 2 | 有可核实的研究 PoC 或受控实验 |
| 3 | 有多个独立利用验证，或可信的实际攻击尝试观测 |
| 4 | 有可信的在野利用记录 |
| 5 | 有权威确认的实际利用，例如适用的 CISA KEV 收录或充分的真实利用证据 |

I 描述有证据支持的潜在技术后果，`consequences.observed` 单列实际观测。不能把 PoC 中的测试数据泄露写成真实客户受害。对可用性问题，初版将可导致服务资源耗尽的路径归入 I=3；这项映射仍需人工校准。

F 越高表示越容易利用。先写出需要的权限、非默认配置和受害者动作，再选择锚点。“零点击”可能仍要求员工正常查询一条受污染记录，这类路径通常适合 F=3。已连接的远程工具返回恶意内容也可落在这个锚点；不能只凭文章中的“无交互”字样统一给 F=5。

S 依据实际披露的版本和部署条件。大厂产品、下载次数、攻击投递目标数量都不能直接换算成受影响部署数。修复版本发布后保留漏洞固有后果，修复状态继续在条目原有版本和建议区域展示。

Activity 使用显式类型，类型和分值必须一致：

| 类型 | A | 所需证据 |
| --- | --- | --- |
| `unknown` | null | 尚不能确定公开利用证据，或尚未完成核查 |
| `confirmed_no_public_evidence` | 0 | 来源明确说明核查范围、时点及未见公开 PoC/在野利用的结果 |
| `attack_path` | 1 | 具体输入、条件与后果组成的可行路径 |
| `controlled_poc` | 2 | 可核实的研究 PoC 或受控实验 |
| `independent_validations` | 3 | 多个独立验证；同一作者的多个演示不够 |
| `observed_attempts` | 3 | 可信的真实攻击尝试，例如带目标载荷的蜜罐请求 |
| `in_the_wild` | 4 | 可追溯的在野利用记录 |
| `confirmed_exploitation` | 5 | 适用的权威确认或充分的真实利用证据 |

查不到攻击记录时使用 `unknown`，不能据此填 0。维护者公告若给出了具体路径，可以评 A=1；这不声称已经排除了在野攻击。CVE 编号不加分，官方来源不自动获得 A=4 或 A=5。CVSS 保持原始来源和版本，已有信息继续保留在正文中，不用 ASO 覆盖。

`confidence` 衡量证据质量：`high` 用于维护者明确说明机制、边界或事故事实的材料；`medium` 用于可追溯但尚未由本站独立复现的研究演示；`low` 表示关键事实仍缺乏核验。这是人工可调整的标注，不从 `sourceId` 自动推断，也不等同于实际利用程度。

## 数据与构建

人工可审查的源文件为 [`content/risk-assessments.json`](../content/risk-assessments.json)。每条记录按最终去重后的 `itemId` 关联；例如 SalesBleed 使用 `pdf-2026-0015`，不使用已合并的旧 ID。

| 字段 | 约束 |
| --- | --- |
| `itemId` | 对应真实存在的最终条目 ID，不允许重复 |
| `ruleVersion` | 每条记录和文件顶层均显式保存规则版本 |
| `dimensions` | 必须显式包含 I、F、S、A；整数或 null |
| `status` | `scored` / `insufficient_evidence` / `not_applicable` / `needs_review` |
| `confidence` | 已建立的配置用 high / medium / low；尚未处理的公开记录为 null |
| `evidence` | 每个已知维度包含一句理由和 `sources` 来源 ID 列表 |
| `sources` | 来源 ID、类型、URL、标题、原文位置、实际读取日期 |
| `activity` | 上表中的显式利用证据类型，必须与 A 对应 |
| `consequences` | `potential` 与 `observed` 分别写潜在后果和实际观测 |
| `reason` | 评估对象，或尚不能给出总分的原因 |
| `assessedAt` | 实际评估日期，不随构建刷新 |
| `reviewed` | 只有人工实际复核后才改为 true |
| `reviewNotes` | 下一次人工复核需核对的条件或争议 |
| `itemFingerprint` | 原条目事实的 SHA-256 指纹，用于发现材料变更 |

`score` 由构建计算。源配置通常不存它；如果提供，校验器要求它与公式及状态完全一致，不能用它覆盖计算结果。

来源 `kind: reference` 的 URL 必须匹配条目已有 reference。补充原始材料用 `kind: primary_url`，并明确标题、原文段落及读取日期。仅有一个合法 URL 不能证明其内容真实，程序只校验结构与关联，内容仍要逐项审阅。URL 限 HTTP(S)，不接受带凭据的地址或脚本协议；页面把理由和来源标题作为文本转义。

`scored` 表示四维证据齐全且通过结构校验，和“已人工复核”分开显示。`insufficient_evidence` 至少有一个未知维度，并写明缺什么。`not_applicable` 的四维全部为 null，并给出来源和判断原因。`needs_review` 用于尚未处理、候选标注或材料变化的记录。未出现在源文件中的条目会获得明确的待评估状态，不会根据标题或标签补分。

构建先完成原有去重、CVE 关联和来源检查，再关联评分，写入 `dist/data/items.json` 的 `riskAssessment` 字段。同时生成 [`dist/data/risk-coverage.json`](../dist/data/risk-coverage.json) 和面向读者的 [`dist/risk-methodology.html`](../dist/risk-methodology.html)。不要直接编辑这些产物。

指纹覆盖原条目的全部字段，排除 `riskAssessment`。键顺序不会改变指纹。事实、日期或来源文字发生变化时，旧总分失效，公开状态变为 `needs_review`，`reviewed` 回到 false。若证据 URL 已从 reference 移除，来源关联校验会直接中止构建，需先修正配置。指纹不监控远程网页变化；网页内容仍需定期人工复查。

## 增加或复核评分

1. 运行 `npm run build`，确认最终事件 ID。读取原始资料及利用条件，选定一个明确机制作为评估对象。
2. 用离线脚本生成候选模板。日期填写实际评估日：

   ```sh
   node scripts/risk-candidate.mjs primary-opencode-mcp-oauth 2026-11-03
   ```

3. 把模板放入 `content/risk-assessments.json` 的 `assessments` 数组。为来源填写 `id`、`kind`、`url`、`label`、`locator`、`accessedAt`，再逐维填写理由与引用。来源 ID 只在这一条评分内使用。未知维度保持 null。
4. 记录潜在后果与实际观测，检查 `activity` 和 A 的一致性。四维完整且依据充分后可设置 `status: scored`，并删除模板里的 `score: null`，交由构建计算。证据不够则设置 `insufficient_evidence`，保留缺口；方法文章可设 `not_applicable`。
5. 人工复核时核对每个数值与原文，检查对象、权限和部署条件。只有实际完成复核才设 `reviewed: true`。材料变化后重新生成指纹，不能仅刷新指纹而跳过证据复查。
6. 运行 `npm run build` 和 `npm test`，在列表和详情页检查解释是否足够。JSON 导出包含完整评分；Markdown 仍按原有事实摘要格式导出。

仓库没有运行时依赖，评分无需联网或付费模型。前端默认仍按日期排序；选择“风险优先”后按分数降序，同分按日期降序再按 ID，未评分条目放在后面。`assessment=scored|pending|not_applicable` 和 `sort=risk` 保存在哈希 URL 中，可与原有筛选组合。

## 版本、校准与后续提取器

同一规则下补证据或纠正判断时，更新评估日期，保留 Git 变更记录。权重、锚点或状态语义改变时发布新 `ruleVersion`，保留旧规则和旧标注快照，显式迁移。初版校验器拒绝未知版本，不混合不同规则的分数排序。

下一步先让两名评估者独立标注同一批记录，记录逐维分歧、未知值比例与来源缺口，再调整规则。当前 15 条样本有选择偏差，尚不足以验证风险预测效果；没有覆盖所有产品，也没有实时核查 KEV 或 EPSS。原始 CVSS 的多来源差异不在本轮归一化。

`createRiskCandidate()` 和命令行脚本已提供离线候选接口，不调用模型。未来 LLM 只负责提取结构化证据与提出分值候选：输入包括事件 ID、原文快照及指纹，输出应包含原文位置、前置条件、潜在后果、实际观测、未知项和候选四维值。总分继续由现有函数计算，模型不能填写任意总分。

接入时将候选存放到单独待审文件，默认 `needs_review`、`reviewed: false`；原文内容只作为数据，不执行其中指令。人工核对出处和锚点后才并入正式配置。留存模型版本、提取提示版本、证据快照、评估者修改及原因；按事件而不是段落划分训练与验证集，避免同一事件泄漏到两侧。未经人工复核的首批配置不能直接当作金标准。

CVSS、EPSS 后续可放在独立外部指标字段中，保存来源、版本和观测日期，通过单独适配器读取；不要回填 I/F/S/A。当前尚未实现这些在线适配器或 LLM 调用。

文案参考 [Lieflat Less AI Tone](https://github.com/larashero3-dotcom/lieflat-less-ai-tone) 的信息守恒和最小改动原则，保留技术限定与证据边界。界面使用原有布局，不增加严重性宣传标签。
